# Design

## Context

The messenger is two repos: a Fastify + Socket.IO backend (`project-js-chat-backend`, in-memory state, sockets joined to `user:<id>` rooms, a client-ack event pattern) and a React 19 + Vite + zustand frontend (`project-js-chat-frontend`) that talks to it through REST (`src/api`) and Socket.IO (`src/socket.ts`). Private one-to-one chats exist as channels with `{ private: true, participants: [a, b] }` (backend `routes.js`), and the frontend derives the peer profile from the active private channel (`ChatPage.tsx`). There is no existing call or WebRTC code anywhere. See proposal.md — Why for motivation.

The call system spans both repos, so this change will touch backend and frontend code even though the OpenSpec root lives in the frontend repo.

## Goals / Non-Goals

**Goals:**
- Real-time voice and video calls, one-to-one, private chats only.
- Screen share during an active call (native picker, camera replaced by the screen).
- Signaling reuses the existing Socket.IO backend and per-user rooms — no external call provider.
- Call connection state (active calls) lives in backend memory only, matching the rest of the server.

**Non-Goals:**
- TURN relay server (STUN-only; strict-NAT may fail) — a separate future task.
- Call history or recording, any persistence of calls.
- Correct multi-tab / multi-device semantics for the same user (a call rings all tabs; only one should answer).
- Group calls / PSTN.

## Decisions

**D1. Signaling over the project's own Socket.IO backend, not an external provider.**
The backend already authenticates sockets, joins them to per-user rooms, and routes targeted events (`app.io.to('user:<id>')`). Call signaling is just three more private-channel-scoped relays. Alternatives considered: Twilio/Agora/etc. — adds a third-party dependency, keys, and cost for little benefit here; a WebRTC data-channel bootstrap — still requires a handshake channel, so it cannot replace signaling.

**D2. Message flow — offer/answer SDP travel inside the call events; `callSignal` carries ICE plus any renegotiation.**
```
Caller                      Backend (user:<id> rooms)            Callee
  getUserMedia, pc, offer      |                                    |
  emit callOffer{callId,channelId,mode,sdp}                         |
  ---------------------------->|  validate private channel member   |
                              |-- callIncoming{callId,peer,mode,sdp}-->|  getUserMedia, pc,
                              |                                    |  setRemote, answer
  <-- callAnswered{callId,sdp}--|<- emit callAnswer{callId,sdp}------|
  setRemote(answer)            |                                    |
  callSignal{callId,{...data}} <-------- relay both ways ----------> (trickle ICE + renegotiation)
  callReject/callHangup{callId} ----------------------------------->  relay as callRejected/callEnded
```
`callId` is generated by the caller via `crypto.randomUUID()` and carried in every event. `callSignal.data` is a union: `{type:'ice', candidate}` | `{type:'offer', sdp}` | `{type:'answer', sdp}` so camera toggles and screen share renegotiate over the same channel.

**D3. Client-generated `callId` + backend keeps a light `state.calls` map.**
The backend stores `{ callId, callerId, calleeId, channelId, mode, phase }` entries purely to detect "busy" (a participant already involved in a live — ringing or active — call) and to clean up on socket disconnect. No per-call persistence.

**D4. `callOffer` outcome is delivered to the caller via the existing ack, with offline/busy/ringing outcomes.**
If the callee has no socket in `user:<calleeId>` → ack `{status:'ok', data:{outcome:'offline'}}`, nothing relayed. If the callee appears in a live call → `{outcome:'busy'}`. Otherwise store the call, relay `callIncoming` to the callee room, ack `{outcome:'ringing'}`.

**D5. Ringing timeout is driven by the caller (≈30 s).** The caller runs a timer and on expiry emits a hangup with reason "no-answer"; the callee also dismisses its ringing prompt at the same timeout. Decline at any time emits `callReject`.

**D6. Frontend architecture — a WebRTC engine + a zustand store + a thin orchestrator, to avoid a store↔socket import cycle.**
`socket.ts` already imports the stores, so stores must not import `socket.ts` back. Instead:
- `src/webrtc.ts` — pure media engine: PC factory (STUN config), `getUserMedia`, `getDisplayMedia`, offer/answer creation, trickle-ICE pump (buffer candidates until remote description is set), `replaceTrack` camera/screen switching, `ontrack` routing, teardown.
- `src/store/calls.ts` — zustand state machine `idle | calling | ringing | active | ended` plus `direction`, `mode`, `channelId`, `peer`, `micOn/camOn/screenOn`, `error`; imports only `types`.
- `src/callManager.ts` — the orchestrator that imports both the store, the webrtc engine and the socket emitters; components and `ChatPage` call only the manager.

**D7. Screen share uses the native `getDisplayMedia` picker (full screen / window / tab) and `replaceTrack`.**
WebRTC does not expose cross-browser pre-selection thumbnails, so a custom picker is not feasible; the native one already offers "a choice of screens". During sharing, the single shared-screen area shows the latest sharer's content (either participant may share; a second sharer replaces the first). The sharer's camera track is swapped out by the screen track and restored (or removed) on stop, per the spec's "Screen replaces the camera" requirement.

**D8. Ringtone via Web Audio.**
No audio assets in the repo; a short repeating two-tone loop generated with an `AudioContext` oscillator avoids bundling files. Played only for incoming calls; stops on accept/decline/timeout.

**D9. Existing patterns are reused.** The ack contract stays `{ status, message?, data? }`; new socket events live inside the existing `app.io.on('connect')` handler next to the messaging events; the frontend reuses `emitWithAck` for `callOffer` and plain emits for the rest.

## Risks / Trade-offs

- **STUN-only media may fail behind strict NAT** → accepted limitation; document it; a future TURN (coturn) task is flagged as optional follow-up and would only add an `iceServers` entry.
- **`getUserMedia`/`getDisplayMedia` require a secure context (HTTPS or localhost)** → dev works on `localhost`; note secure-host requirement for anything remote.
- **Multi-tab: one user's call rings in every open tab** → accepted as non-goal. Cheap safety: when the callee accepts, the backend also broadcasts an `active` notice to the callee room so sibling tabs can dismiss their ringing prompt; full multi-device semantics remain out of scope.
- **Race: both participants call each other simultaneously** → the second `callOffer` hits a busy callee (they already appear in a live call) and gets `{outcome:'busy'}`; acceptable and spec-aligned.
- **Tab reload during a call loses media** → socket disconnect triggers backend cleanup, which notifies the peer (`callEnded`) and clears the call state; the peer sees the call drop.
- **Screen share unavailable on some mobile browsers** → feature-detect `getDisplayMedia` and hide the screen-share control where unsupported.

## Migration Plan

No data migration. Ship backend and frontend together: add the socket events + `state.calls` on the backend, then the frontend `webrtc.calls`/UI modules. Rollback = revert both sides (removing the new socket events and UI; older clients simply ignore unknown events, and unreferenced UI has no effect). The call system is additive — existing messaging, contacts and auth behavior is untouched.

## Open Questions

None. Remaining unknowns (e.g., capturing system/tab audio as a share option, portrait-mirror of the self view, styling details) are cosmetic or additive and do not change the specs, architecture, or task breakdown.
