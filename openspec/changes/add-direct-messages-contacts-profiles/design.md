# Design

## Context

Текущий бэкенд (`project-js-chat-backend`) держит всё состояние в памяти (`state` в `routes.js`: `users`, `channels`, `messages`), JWT-токен отдаёт только REST (`/login`, `/signup`, `/data`), а сокеты не аутентифицированы вовсе (`// TODO add socket auth` в `plugin.js`) и вещают всем подписчикам через `app.io.emit`. Фронтенд — React + Zustand + `socket.io-client`: `/data` грузится один раз, события `newMessage`/`newChannel`/`renameChannel`/`removeChannel` раскладываются в `useChatStore`; авторизация — Bearer-токен в `localStorage`. Мотивация и скоуп — в `proposal.md`.

Ключевые ограничения, которые формируют дизайн:
- Ник уникален и является единственной идентичностью в `Message.username` (без `userId` в сообщениях).
- Канал — это `{ id, name, removable }`: понятия «участники» и «приватность» сейчас нет.
- Сокет подключается до/без токена; приватность событий невозможна без аутентификации.

## Goals / Non-Goals

**Goals:**
- Приватные одно-на-один чаты с доставкой только двоим участникам (выбран вариант B из обсуждения).
- Поиск по нику, просмотр профилей, запросы на добавление в контакты с баннером «хочет добавить вас в контакты» (принять/отклонить).
- Редактирование профиля: смена ника (с переприсвоением истории) и аватарки.
- Сохранить существующие публичные каналы и их поведение без изменений.

**Non-Goals:**
- Групповые приватные чаты, блокировки пользователей, статусы «онлайн/печатает», непрочитанное.
- Редактирование/удаление сообщений, поиск по email.
- Персистентность бэкенда (остаётся in-memory) и кроппинг/обработка аватарок на клиенте.

## Decisions

### D1. Аутентификация сокетов через комнаты `user:<id>`
`io.use`-middleware в `plugin.ts` валидирует `socket.handshake.auth.token` через `app.jwt.verify`, кладёт `socket.userId` и делает `socket.join(\`user:${userId}\`)`. Публичные события по-прежнему `app.io.emit`, приватные — `app.io.to('user:'+a).to('user:'+b).emit(...)`. Это закрывает существующий TODO и даёт масштабирование приватности без переделки клиентской логики (фронт по-прежнему получает событие и кладёт в стор).
- Альтернатива (отказ от socket auth, приватность только в UI) — отклонена пользователем в пользу реальной приватности.

### D2. Приватный канал как сущность с `participants`
`Channel` получает необязательные `private?: boolean` и `participants?: number[]`. Приватный (ЛС) канал: `name = ник собеседника`, `participants = [a, b]`, `removable = false`, `private = true`. Уникальность пары — поиск канала, где `participants` содержит обоих в любом порядке; создание идемпотентно (существующий возвращается, дубли не плодятся). Маршрутизация событий — по D1: если у канала есть `participants`, рассылка только по этим комнатам.

### D3. Состояние контактов: `user.contacts` + `contactRequests`
- `user.contacts: number[]` — принятые контакты (взаимообразно).
- `contactRequests: [{ id, fromUserId, toUserId, channelId, status: 'pending' }]` — только pending-запросы; принят/отклонён → запись удаляется.
- Запрос создаёт/переиспользует ЛС-канал пары (чтобы баннер мог сесть над существующим чатом — требование specs).
- При принятии: оба получают друг друга в `contacts`, отправителю уходит событие.
- При отклонении: отправителю уходит событие; чат остаётся; отправитель может послать запрос снова.

### D4. REST для операций, socket для пуш-уведомлений
Операции (поиск, запрос, принятие/отклонение, удаление контакта, правка профиля) — REST с Bearer-токеном, как существующие `/data`/`/login`. Пуш реального времени — сокет-события на участников:
- `contactRequest` → получателю (id + профиль отправителя + channelId)
- `contactRequestResolved` → отправителю (accepted/declined)
- `userUpdated` → всем (при смене ника/аватарки; фронт переписывает ники в истории и в списках)

Это держит контракты тестируемыми (`curl`) и решает только реалтайм через сокеты.

### D5. Смена ника переприсваивает историю по `username`
Сообщения не носят `userId`; переименование переписывает `username` во всех сообщениях автора и в `name` его ЛС-каналов (они названы ником собеседника). Уникальность нового ника проверяется до записи (409). После успеха уходит broadcast `userUpdated`, онлайн-клиенты переписывают ники в `messages` и списках. Оптимальность (индексы, мгновенность) не критична: состояние в памяти.
- Альтернатива (хранить `userId` в сообщениях и резолвить ник при отрисовке) требует изменения контракта `/data` и `types.ts` по всей глубине — отложена (см. D7).

### D6. Аватарки отдельным эндпоинтом
`POST /api/v1/avatars` — multipart, только `image/*` (png/jpeg/gif/webp), лимит 1 МБ, запись файла по образцу `storeUpload`. Отдельный эндпоинт, а не перегрузка сообщениевого аплоада: позволяет задать свои ограничения и не смешивать семантику. Возвращает `{ url }`; профиль обновляется через `PATCH /users/me { avatarUrl }` / `{ avatarUrl: null }` для удаления. Плейсхолдер — круг с первой буквой ника (генерируется на фронте).

### D7. `/data` скоупится под текущего пользователя
`GET /api/v1/data` возвращает пользователю: публичные каналы + его ЛС-каналы, сообщения только этих каналов, `me`, `contacts` (профили), `requests` (входящие pending). Отправка своего профиля в `/data` убирает отдельные `GET /users/me`; поиск по нику — `GET /users/search?query=` (возвращает публичные профили `{id, username, avatarUrl}`, без email, минус себя).

## Risks / Trade-offs

- Сокет не переподключается с протухшим токеном → клиент увидит disconnect; фронт при `socket.connect_error` с невалидным токеном очищает сессию и показывает логин. Реальное истечение JWT сейчас не задано (`app.jwt.sign` без `expiresIn`) — риск низкий.
- Переименование переписывает историю по `username`, а не по `userId` → если когда-либо сообщения начнут хранить `userId`, логика сменится. Это фиксированная цена in-memory backend'а, приемлемая здесь.
- Файлы старых аватарок на диске не удаляются → мусор в `uploads/`; для учебного проекта допустимо, отметить как известное ограничение.
- Broadcast `userUpdated` всем меняет ники даже у тех, кто не знает пользователя → клиент фильтрует по наличию авторства (messages/contacts), лишних перерисовок нет.
- Орфан-состояние при двух одновременных запросах в обе стороны → сервер отдаёт один канал и один pending-запрос (идемпотентная проверка по паре).

## Migration Plan

- Бэкенд и фронтенд разрабатываются и деплоятся вместе (бэкенд in-memory, данные теряются при рестарте — миграции данных нет).
- Откат: revert коммита в обоих репозиториях и рестарт сервера.
- Обратная совместимость: старые клиенты без socket auth будут отвергнуты middleware (breaking, согласовано в proposal). `/data`-паддинг для старых клиентов не требуется — приложение деплоится целиком.
